# Parent paths as traversal-certificate witnesses

Recorded UTC: 2026-10-01T01:56:03.995693+00:00. Source-only feasibility review at querygraph/sail `fc094a0c25a49edeac2f9f0195aa973421a21a43` after fetching `origin` and `querygraph`. No implementation, SQL engine, build, benchmark, remote-host operation or existing evidence change.

A total rooted parent tree with bounded integer hops **can replace the extra tight-edge reachability traversal**, provided every chosen parent edge passes the **same certificate candidate/allowed expression** and all existing input, distance, edge and parent-output checks remain enforced. This is a feasible change, not an implementation verdict or measured speedup.

The current [certificate](https://github.com/querygraph/sail/blob/fc094a0c25a49edeac2f9f0195aa973421a21a43/examples/extensions/benchmarks/traversal_certificate.py#L22) validates complete vertex coverage, finite nonnegative distances, source zero, valid endpoints/weights, orientation, finite relaxation sums, reachability closure and all-edge inequalities. It then constructs tight edges and performs a separate materialized breadth-first witness traversal ([lines 44–84](https://github.com/querygraph/sail/blob/fc094a0c25a49edeac2f9f0195aa973421a21a43/examples/extensions/benchmarks/traversal_certificate.py#L44)). The caller subsequently runs [parent validation](https://github.com/querygraph/sail/blob/fc094a0c25a49edeac2f9f0195aa973421a21a43/examples/extensions/benchmarks/traversal_cell.py#L107), including unreachable-null consistency, source self-parent/hops zero, bounded hops, parent linkage and parent-edge existence ([lines 140–165](https://github.com/querygraph/sail/blob/fc094a0c25a49edeac2f9f0195aa973421a21a43/examples/extensions/benchmarks/traversal_cell.py#L140)). The proposed change concerns only how source-rooted witness coverage is proved.

For every reached non-source vertex v, require an existing reached parent p, finite distances, non-null integral hops, `h(v) = h(p) + 1`, and `1 <= h(v) < V`. Require the unique source to have hop zero and forbid hop zero on any other reached vertex. Following parents strictly decreases nonnegative integer hops, so it cannot cycle and must terminate at the source. Reversing that chain gives a source-to-v path of at most V−1 directed tight edges. Zero-weight cycles, arbitrary signed vertex IDs and duplicate edges do not invalidate this proof. ID ordering is irrelevant; hop ordering matters.

Retain every existing all-edge check. A valid tree alone does not show optimal distances or complete reachability: an undiscovered shortcut or incorrectly unreachable neighbor still requires the all-edge inequalities/closure checks. The existing global `slack`, maximum candidate and `(V−1)*(slack + ulp(maximum_candidate))` bound can remain unchanged ([lines 85–94](https://github.com/querygraph/sail/blob/fc094a0c25a49edeac2f9f0195aa973421a21a43/examples/extensions/benchmarks/traversal_certificate.py#L85)); derive them from all links, not just parent edges. This source also explains the previously reported logging03 bound's addition of a rounding term; the closed review correctly left its earlier unsupported edge-only formula unclaimed.

Three compatibility details block a mechanical substitution:

- **The numerical predicates differ.** The certificate computes `candidate = parent_distance + weight` and then `abs(distance - candidate) <= tolerance + tolerance*abs(parent_distance) + tolerance*abs(weight) + tolerance*abs(distance)`. Existing parent validation uses `abs((distance - parent_distance) - weight) <= 1e-12*(1+abs(distance))`. For parent distance 1, weight 1 and child distance `2 + 4e-12`, the certificate accepts tightness while the old parent predicate rejects. Changing the old parent test to the certificate expression alone would broaden the existing parent-output acceptance contract. Initially retain that old test as an additional requirement, and use the certificate's already-computed `candidate`/`allowed` relation to establish the witness. Binary64 regrouping itself also differs: `(1−1)−2^-53` is nonzero, while `1−(1+2^-53)` is zero. Do not assume algebraic equivalence or rely on a recomputed/substituted tolerance.
- **Parent depth is not BFS witness depth.** On zero-weight edges 0→1, 1→2 and 0→2, the valid supplied parent chain 0→1→2 has maximum hop 2, while the certificate BFS finishes in one round. A cap of 1 currently passes. Therefore rejecting solely because maximum supplied hops exceed the cap changes existing outcomes. To preserve them, use the parent fast path only when its maximum hop is within the existing cap; otherwise keep the existing BFS fallback. Alternatively redefining the cap as an implementation work budget is a separate explicit policy change. Validate the cap argument even on the fast path.
- **SQL nulls and dropped joins cannot serve as proof.** An inner join can silently discard a missing parent; `WHERE NOT(h = parent_h + 1)` does not select an UNKNOWN comparison. Keep total row coverage, left/anti-join absence checks and explicit null rejection. Current `validate_parents` combines these with checks over every reached row. The proof should explicitly admit integral hop types; do not generalize arithmetic reasoning to arbitrary floating hop values. Existing Pecan construction casts hops to long and Argentea stored-output validation requires LongType, but a new generic validator must not infer a schema from a column name.

Distance-only native outputs must retain the current BFS witness path. Portable outputs must still fail if mandatory parent/hop columns are missing. When both are present, invalid parent metadata must remain an error rather than silently selecting a fallback that ignores it. One missing optional native column currently yields no parent check; any stricter schema policy should be separately named. Reference-vector validation and its tolerance should remain unchanged.

A minimal implementation route is to form the existing validated all-edge `links` once, derive the same tight `(src,dst)` relation, and check that every non-root reached `(parent,id)` pair appears in it. Keep the existing parent-output numeric condition unless an explicitly reviewed contract change is desired. Run the integer-hop/root/totality checks before accepting that witness. The original traversal remains available for distance-only outputs and cap-preserving fallback. Record which witness method ran; do not label maximum parent depth as measured BFS rounds. Existing `witness_rounds` consumers and tests need a small audit before a new method is published.
