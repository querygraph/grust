## How classes were assigned

- A failure test is COVERED when the same input gives the same condition and parameters from the function the run path calls, and the call site was confirmed by reading.
- A "does NOT fail" test is PARTIAL when Sail checks only the validator and Spark requires the following run to complete.
- A cited Rust port does not count as coverage if it goes through a path production skips. Two paths matter:
  - `tests/run.rs` and `tests/write.rs` use `run_flow`/`handle_microbatch`. Production uses `run_durable_flow`. The prepare and merge functions are shared; enrolment and reset are not.
  - The `full_refresh` helpers in `tests/run.rs` call `materialize::tables`. `execution::execute` removes CDC targets from that selection.
- Python tests using the `broker` fixture skip when `SAIL_IGGY_SERVER_BINARY` is unset. That includes every test in `test_autocdc_iggy.py` that takes `broker`, and most of `test_autocdc_spark_suites.py`. Coverage that rests only on them, such as FullRefreshSuite:40 and :97, needs that binary in the gate.

## Likely behaviour gaps, most user-visible first

All are inferred from code, not observed. Each names the cheapest experiment that would refute it.

1. **Full refresh does not do what the error messages tell the user to do.**
   - The KEY_SCHEMA_DRIFT message says "To change keys, perform a full refresh". The three AUXILIARY_TABLE_* messages say a full refresh recreates the auxiliary table.
   - Spark drops the auxiliary table in `DatasetManager`, before the flow starts, so drift has nothing to compare.
   - Sail's `run_durable_flow` calls `ensure_auxiliary_table`, which validates drift, before the reset branch. `finish_reset` then truncates the table (`durable.rs` "Truncating keeps both tables and their identities").
   - So a key change with `--full-refresh` should still fail with KEY_SCHEMA_DRIFT, and corrupt metadata should stay unrecoverable.
   - Related, less certain: a reset keeps the old schemas, so a type change under full refresh is not replaced as Spark's is.
   - Experiment: run, change `keys`, run with `full_refresh_all=True`.
2. **Dropping the auxiliary table stops the run instead of being repaired** (AuxiliaryTableDurabilitySuite:184).
   - `ensure_auxiliary_table` recreates the table with a new Delta identity, then `enroll` passes it to `transitions::enroll`, which returns IdentityMismatch when `guard.auxiliary != auxiliary`.
   - The authority persists at `<warehouse>/_control/authority.db`.
   - `a_dropped_auxiliary_table_is_recreated` passes only because the test path has no enrolment. `a_recreated_table_is_not_adopted` pins the refusal on the production path, though with both identities changed.
   - Full refresh cannot help, because enrolment runs before the reset.
   - Experiment: run, `DROP TABLE __spark_autocdc_aux_state_target`, run.
3. **A full refresh of a target that does not exist yet does not create it.**
   - `CdcRun::prepare` computes `missing` from `selection.refresh` only. `Selection::new` puts full-refresh names in `reset`, and the two sets cannot overlap.
   - `execute` also subtracts CDC targets from the plain selection, so nothing creates the table, and `lacks_commit_timestamps` should fail with not-found.
   - Spark's suites do not cover a first-run full refresh directly; this is a user-visible difference found while reading.
   - Experiment: `full_refresh_all=True` on a fresh pipeline.
4. **Dry run does not run the flow-schema validators.**
   - Spark constructs `AutoCdcMergeFlow` during resolution, so AUTOCDC_KEY_NOT_IN_SELECTED_SCHEMA, AUTOCDC_COLUMNS_NOT_FOUND_IN_SCHEMA and AUTOCDC_RESERVED_COLUMN_NAME_PREFIX_CONFLICT fail a dry run.
   - In Sail, `output_field_names` is reached only from `flow_output_schema`, and that only from `CdcRun::prepare` and `evolved_schema`. `analysis.rs` does not mention AutoCDC, and `mod.rs` skips `execute` on a dry run.
   - A real run still fails before any write, so only the dry run differs. No Sail test passes a bad key end to end.
   - Experiment: dry run with `keys=["absent"]`.
5. **Analysis sees the wrong schema for an AutoCDC target.**
   - The comment on `with_output_schemas` says analysis gives the target the schema of the feeding query. `CdcRun` corrects its own copy, not `analyzed.schemas`.
   - Spark's Flow.scala says downstream sees the augmented schema.
   - A downstream view selecting `__spark_autocdc_metadata` should fail analysis, and one selecting an excluded column should pass analysis and fail later.
   - `test_an_autocdc_target_feeds_a_materialized_view_in_the_same_graph` selects only columns present in both schemas.
   - Experiment: a materialized view in the same graph selecting the metadata column.
6. **Diagnostics only, not user-reachable or low value.**
   - DATATYPE_MISMATCH.CAST_WITHOUT_SUGGESTION is absent (BatchProcessorSuite:640), and production passes the batch's own type.
   - AMBIGUOUS_REFERENCE for the reserved winning-row name (:390) is unreachable behind the reserved-prefix check.
   - `reconcile::field_index` raises an internal error where Spark raises an analysis error, reachable only if validators were skipped.

## Corrections to existing evidence

- `target_key_comparison_respects_case_sensitivity` claims the gridTest's two arms and runs one.
- The three `tests/run.rs` full-refresh ports exercise a path production does not take, and assert a drop where production truncates.
- `CDC-UNITS.md` (found at `grust-sdp-fable/docs/sail-declarative-pipelines/`) reports the dropped-table and full-refresh cases as ported. They are ported only at those test paths.
- The params comment in `test_autocdc_definition.py` and `tests/graph.rs` for the materialized-view case is stale; `test_connect_invalid.py` asserts them.
