# Session deletion state/ownership audit

Read-only source audit at Sail `ec8e74d57de51149a774cd4f9048d82039704d0c`, `/Users/alexy/src/sail-pipelines-proposal`. All source references below were revalidated against that commit; no builds or repository edits. Recommendations describe a proposed contract, not implemented guarantees. The separate checkpoint-effect and cluster audits still determine how much cleanup can actually be certified.

Concrete qualification dependency: the parallel `/tmp/sail-sdp-checkpoint-effect-audit.md` finds runtime-wrapper PUT/multipart tasks that survive cancellation (`sail-object-store/src/layers/runtime.rs:75–105,255–266,292–309`, with an existing cancellation test at `520–535`). Its object-store and dependency inspection was not duplicated here. Consequently the state/waiter unit can establish accurate completion of the current helper, but must not advertise a storage-effect barrier or certify that no checkpoint can reappear. Full deletion acknowledgement requires those effects to be joined or to enter the runner's cleanup result as explicit uncertainty that prevents prefix deletion. Keep this prerequisite visible rather than treating the current helper's Ok as stronger evidence.

Current behavior and seams:

- `crates/sail-session/src/session_manager/session.rs:11–31`: only Creating, Running, Deleted, Failed; Creating owns creation waiters, Running owns context/driver identity. There is no pending deletion/result owner.
- `session_manager/actor/handler.rs:269–294,297–330`: idle and explicit deletion start background cleanup, immediately remove the driver entry, replace Running with Deleted, and emit DELETED. Explicit deletion immediately replies `Ok(())`. `handler.rs:373–390` obtains JobService, then starts `ctx.spawn`; missing service only warns, and later cleanup errors only warn.
- The new helper is correct within its stated boundary: `session_manager/actor/cleanup.rs:7–16` awaits `runner.stop()?` before checkpoint cleanup and propagates its result. It does not qualify actor state or RPC acknowledgement.
- `session_manager/mod.rs:63–72` already waits for a result-bearing oneshot. The sole production delete caller found is Spark Connect `crates/sail-spark-connect/src/server.rs:450–470`, which awaits that method before returning ReleaseSessionResponse. No wire change is needed to delay acknowledgement. `allow_reconnect` is explicitly unsupported at lines 456–457.
- `handler.rs:35–60` never recreates an existing Deleted/Failed entry; retained tombstones already prohibit session-ID reuse. Context clones returned before a deletion remain usable references, so a registry-state change alone is not an execution/effect fence.
- Creation is actor-serialized, but activation is asynchronous: `handler.rs:153–179,183–245`. CompleteSessionCreation currently checks Creating plus matching optional driver ID, which is None for all local sessions. Delete while Creating currently returns an error rather than accepting cancellation.
- `handler.rs:333–369` SetSessionFailure can overwrite any state with Failed and drops Running context ownership; it must not erase a future Deleting operation. The pinned whole-crate search found its message/handler but no producer. That is not proof no future or external internal-module caller can exist.

Recommended smallest state contract:

| State | Retained ownership | get/create | delete |
| --- | --- | --- | --- |
| Creating | Existing activation/creation owner and waiters | Join creation | Keep existing explicit in-progress error for this unit |
| Running | SessionContext and optional driver ID | Return context and track activity | Atomically enter Deleting; attach first waiter; launch exactly one cleanup operation |
| Deleting | Context/cleanup inputs, driver identity, unique attempt token, shared terminal outcome, waiter list | Reject; never return the old context or create a replacement | Join the same operation; no second stop/checkpoint deletion |
| DeletionFailed | Retained cleanup owner, stage, typed terminal error and attempt identity | Reject | Return the retained typed error by default; no implicit retry or resurrection |
| Deleted | Existing tombstone | Reject | Return success idempotently for this known completed deletion |
| Failed | Existing creation/general failure semantics | Reject | Keep explicit error until that failure's cleanup ownership is separately qualified |

Adding DELETING and DELETION_FAILED status strings does not require an enum migration: `crates/sail-system-store/src/event.rs:19–29` stores String statuses; `event.rs:98–100` recognizes only DELETED; `engine/mutation.rs:197–211` sets deleted_at only on DELETED. Emit DELETING on accepted deletion, DELETION_FAILED on failure, and DELETED only after successful required cleanup. Status reporting is telemetry, not a substitute for the actor's authoritative result or a requirement to wait for telemetry persistence.

Make the intentional behavior change explicit: repeated deletion of a known Deleted tombstone returns the completed success so a caller can recover a lost RPC response. For public Spark ReleaseSession parity, an unknown ID also returns success without creating an entry or tombstone; the existing Sail invalid/not-found behavior is not the Spark target. Reconnect stays unsupported. The pinned Spark evidence and precise test strength are recorded in the addendum below.

The operation should reuse Sail's actor shape, not block `receive`:

1. Move Running ownership into Deleting synchronously in the handler. Keep the driver registered while shutdown needs gateway callbacks; `handle_get_driver` is independent of session state (`handler.rs:25–32`). Do not remove the registry entry merely because cleanup was scheduled.
2. A single actor-owned task drives stop and then checkpoint cleanup. Retain a shared terminal result in the operation itself; send `CompleteSessionDeletion { session_id, attempt }` only after recording that result. The message is notification, not the sole owner of the result or cleanup inputs. No per-waiter forwarding task is necessary.
3. Construct an interruption/panic completion guard before spawning, following the managed-stream cleanup-owner pattern. Otherwise `ctx.spawn` panic/abort before its first poll can leave Deleting and waiters stranded. An interrupted operation publishes an explicit failure and keeps resources reachable; it never fabricates success. Catch foreign cleanup panics outside actor state mutation and preserve ordinary typed errors.
4. Completion handling accepts only the matching Deleting attempt, applies the terminal state once, emits the corresponding status, and fans the immutable result out to all waiters. Ignore stale/duplicate notifications; dropping a waiter is harmless. Prune closed senders on admission/completion so abandoned callers do not accumulate indefinitely.
5. Store failures as shared `Arc<DataFusionError>` or an equivalent report retaining the original cause. Fan out `SessionError::DataFusionError(DataFusionError::Shared(error.clone()))`, rather than cloning error strings. `crates/sail-session/src/error.rs:11–19` and `crates/sail-spark-connect/src/error.rs:153–160` already carry that typed path. Missing JobService becomes a deletion failure; it cannot be logged and treated as cleanup success.

Concurrency and failure rules:

- **Concurrent deletes / dropped RPC:** the actor orders requests. The first accepted delete owns the work; subsequent requests attach waiters. Cancellation or timeout of an RPC only drops its waiter. It cannot cancel the task, reopen admission, or permit namespace cleanup ahead of stop. Completion remains observable by a later delete even if every original waiter disappeared.
- **Idle deletion:** after the existing ActivityTracker check at `handler.rs:275–279`, use the same begin-deletion helper with no waiter. An explicit delete arriving later attaches to it. Repeated idle probes in Deleting/DeletionFailed/Deleted do nothing. Existing activity timestamps (`sail-common-datafusion/src/session/activity.rs:26–40`) are sufficient while session IDs cannot be reused.
- **Lookup race:** lookup handled before delete can return a context; lookup handled after the state change rejects. Runner admission is sealed when stop is polled, not when its future is constructed. Jobs admitted through an earlier context before that seal must be included in stop; later admissions reject. Current LocalJobRunner supplies that narrower fence (`sail-execution/src/job_runner/local.rs:155–205`). This does not fence commands or effects that bypass the runner, which require the parallel effect audit.
- **Creation race:** preserve rejection of delete during Creating for the smallest unit. It must return an honest in-progress error, not claim deletion. Supporting accepted deletion during activation is a larger follow-up: Creating currently does not retain its context; that context is captured by CompleteSessionCreation. Such support would need to own/cancel or join activation, fail creation waiters, and prevent a late creation completion from resurrecting Running.
- **Generation/stale completion:** give each accepted deletion attempt a checked, monotonic actor-generated token. Match both session ID and token before applying completion. With retained tombstones and no session-ID reuse, an attempt token is sufficient; do not invent incarnation reuse now. If reuse is ever enabled, creation completion, idle probes, failure notifications and deletion completion all need the same incarnation fence. The existing optional driver-ID check is not a local-session generation token.
- **SetSessionFailure race:** add explicit Deleting/DeletionFailed/Deleted handling. It must not overwrite the retained deletion owner or reopen a terminal state. A matching failure affecting cleanup should be retained by the same operation; a stale notification should be ignored. The current ID-only message cannot distinguish incarnations if reuse is later introduced. Running→Failed currently also bypasses runner cleanup and needs its own ownership decision; do not silently declare that path fixed by explicit-delete changes.
- **Failure recovery:** keep the session inaccessible and preserve ownership/error. Do not automatically retry unknown-commit/uncertain stop results; LocalJobRunner deliberately retains cleanup failures across repeated stop (`local.rs:182–229`). A subsequent successful join does not erase historical uncertainty. Checkpoint-cleanup-only retry may be a future explicit operation if the checkpoint audit establishes an idempotent retry contract; retain the last completed phase so it cannot accidentally skip an unconfirmed stop. Never restore Running after stop has sealed the runner.

Graceful shutdown is an essential ownership interaction, not a mailbox detail. `sail-common/src/actor.rs:436–443` closes the mailbox before calling actor.stop and aborts remaining context tasks afterward. `ActorContext::spawn` returns only an AbortHandle (`actor.rs:135–138`); reap logs task failures (`145–155`). Therefore deletion completion cannot depend solely on sending a message back to the actor. The retained shared outcome must be directly awaitable/finalizable from `SessionManagerActor::stop`, while its cleanup tasks and gateway remain alive. Existing manager stop (`session_manager/actor/core.rs:120–136`) drains drivers, joins children and stops the gateway; it does not stop local runners or await deletion tasks. At minimum, the deletion unit must join/finalize accepted in-progress deletions there before their owners are dropped. Bringing every Running/Creating session into graceful shutdown and changing the Shutdown result from unit to a typed aggregate are separate larger changes if not included in this unit; do not advertise manager-wide cleanup until they are done. Process abort/runtime loss cannot be promoted into successful deletion.

Existing proof and proposed tests:

- `session_manager/actor/cleanup_tests.rs:24–70` provides a delayed/error TestRunner; `81–92` gives the real checkpoint descriptor fixture; `95–185` proves typed failure preservation, cleanup ordering and stopping without a checkpoint registry. These helpers are private and do not test actor state, waiter ownership, RPC acknowledgement or status events.
- No session-manager actor lifecycle tests were found in the pinned `sail-session` source inventory. Existing injection seams are `SessionManagerComponents` (`actor/options.rs:18–23`), `SessionFactory::create` (`session_factory/mod.rs:18–23`), and `SessionManager::try_new` (`session_manager/mod.rs:37–44`). A small test factory can install a controlled JobService and registry while using the ordinary local runner factory; no production constructor expansion is required solely for tests. RuntimeHandle::new is public (`sail-common/src/runtime.rs:52–55`).
- Add actor-driven latch tests: delayed stop keeps both delete replies pending and a different session responsive; checkpoint cleanup starts only after stop success; stop/checkpoint error reaches every waiter with typed causes; all waiters dropped still completes; explicit delete joins idle deletion; get/create rejects during and after deletion; stale completion cannot transition a newer attempt; SetSessionFailure does not discard a pending owner; graceful manager shutdown waits for an accepted deletion without relying on its closed mailbox. Assert DELETING/DELETION_FAILED do not set deleted_at and only successful completion does.
- Public ReleaseSession tests must call the raw stub and observe its future/result. `python/pysail/tests/spark/pipelines/test_session_graphs.py:72–76` already uses that RPC but only in teardown. Routine session fixtures suppress stop exceptions, so their success cannot prove deletion error propagation. Prefer gates/oneshots or actor message barriers over elapsed-time assertions; use the existing controlled runner/registry patterns for pending and failure behavior.

Scope boundary: delayed acknowledgement is truthful only for the cleanup work that the operation actually owns and awaits. This state change alone does not strengthen ClusterJobRunner's remote acknowledgements, stop unregistered execution tasks, join every Spark operation/pipeline driver, or prove target-commit/checkpoint atomicity. Keep those qualifications explicit when naming terminal statuses and claiming release semantics.

Spark parity addendum (pinned Spark `617618396087429b5627a86ce933bb0f5d6645cb`; source-only review):

- `sql/connect/server/src/main/scala/org/apache/spark/sql/connect/service/SparkConnectReleaseSessionHandler.scala:29–45` explicitly treats an absent session as a no-op, calls closeSession, then sends a response. It only sets serverSideSessionId when a holder was present (`35–38`); Sail's existing response-ID behavior at server.rs465–468 is a separate compatibility point, not proof of cleanup.
- `sql/connect/server/src/main/scala/org/apache/spark/sql/connect/service/SparkConnectSessionManager.scala:227–248,262–266` only adds a closed-session cache entry and shuts down a holder inside `Option.foreach`. A never-seen ID therefore succeeds without creating a tombstone. For known sessions, the closed-session cache is populated **before** removal to prevent a recreation race (`232–246`); `368–382` validates new session creation and rejects a cached closed ID. Preserve Sail's existing known-session tombstone principle while making unknown ReleaseSession a no-op.
- `sql/connect/server/src/test/scala/org/apache/spark/sql/connect/service/SparkConnectServiceE2ESuite.scala:53–69` invokes client.releaseSession twice (`62–64`) without an exception assertion; this pins successful repeat/no-op behavior, not a specific second response payload. Query cancellation is then checked with Eventually (`66–69`), so this original test does **not** prove all effects are joined before release returns. `78–89` allows cancellation or session-closed errors for old queries; `91–95` checks that a later interruptAll request is rejected with INVALID_HANDLE.SESSION_CLOSED.
- Suggested public assertions: release a fresh valid UUID twice, then successfully create its first session (unknown release must not reserve the ID); release a known session twice successfully, then reject recreation/use of that known closed ID. Keep cleanup-latch/error propagation tests separate from these protocol no-op assertions.
