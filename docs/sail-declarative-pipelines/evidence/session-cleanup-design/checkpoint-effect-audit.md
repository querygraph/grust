# Checkpoint effects and session deletion: source audit

Sail pin: `ec8e74d57de51149a774cd4f9048d82039704d0c`, inspected with `git show` in `/Users/alexy/src/sail-pipelines-proposal`. Read-only; no builds, tests, fault injection, or source changes. The schedules below are deterministic test designs supported by source, not observed runtime failures. Dependency files are the installed sources matching Cargo.lock; their hashes accompany this report in `/tmp/sail-sdp-checkpoint-effect-sources.json`.

## Finding

The new local runner owns admitted preparation, stream disposal and registered resource supervisors. It does **not** yet establish a checkpoint-storage effect barrier. A checkpoint PUT or multipart completion can remain active on the object-store runtime after its consumer future is dropped and local stop returns success. A subsequent prefix listing/deletion can therefore finish before the object appears. Delaying the session delete acknowledgment until the existing cleanup helper returns would improve acknowledgment honesty only for that helper's current, narrow contract; it would not prove that checkpoint storage is quiescent.

The clearest source is Sail's own runtime wrapper, independently of provider cancellation semantics: `crates/sail-object-store/src/layers/runtime.rs:75–105` spawns PUT and multipart creation and awaits ordinary JoinHandles; `:255–266` similarly spawns multipart completion. Dropping the awaiting future does not abort or join those tasks. `:292–309` starts a detached Drop cleanup task, waits at most 15 seconds for parts, serializes behind completion, and logs abort errors. No result is registered with an execution scope. The existing `cancelled_completion_does_not_abort_committed_upload` test (`:520–535`) explicitly permits completion after its caller is canceled. That behavior needs an owner visible to session cleanup, not an assumed abort.

## Execution and publication chain

- `sail-spark-connect/src/service/plan_executor.rs:528–563`: only eager remote checkpoint commands are admitted; a fresh relation UUID is generated, then normal plan execution produces the cached relation response. `:566–574` does no relation-release cleanup; checkpoints have session lifetime.
- `sail-session/src/planner.rs:182–219`: physical planning resolves and captures a relation prefix before runner execution. `RemoteCheckpointWriteExec` writes partitions and `RemoteCheckpointCommitExec` publishes the descriptor. `:220–227` reads the descriptor for later checkpoint scans.
- `sail-physical-plan/src/remote_checkpoint.rs:356–400`: commit execution wraps `commit_checkpoint` in `stream::once`; it is owned by the returned stream. `:542–569` similarly wraps each partition write. Neither operator registers a TaskResourceScope supervisor; bounded `git grep` over this file confirms no use of that API.
- `:573–650`: the partition writer reads input, constructs a single-file ParquetSink, awaits `write_all` (`:630`), awaits object HEAD (`:631–635`), then emits partition metadata. An empty/zero-column partition creates no object. Partition files use a UUID suffix (`:549–552`).
- `:654–698`: commit collects every partition descriptor, synchronously calls registry.insert, then returns an empty command batch. On a returned error it awaits relation-prefix deletion. Dropping this future does not execute that error arm; there is no Drop guard. A complete descriptor is only published after collected metadata, but storage may already exist before publication.
- `sail-object-store/src/registry.rs:98–109`: dynamically created stores are wrapped in RuntimeAwareObjectStore. Explicit `register_store` at `:89–95` can bypass this wrapper, so mock/custom stores need their own effect contract.
- `sail-execution/src/job_runner/local.rs:269–300` installs a fresh resource scope before execution; `:155–205` cancels streams and awaits their registered scope reports. `:313–314` explicitly excludes unregistered operator tasks/remote effects. `sail-common-datafusion/src/managed_stream.rs:329–350` drops the source stream, then drains only that scope.

Dependency detail reinforces the gap. Cargo.lock pins DataFusion 55.2.0 and object_store 0.13.2. DataFusion `datafusion-datasource/src/file_sink_config.rs:119–135` starts a demux task; `datafusion-datasource-parquet/src/sink.rs:283–359` starts writer JoinSet tasks, joins them on the ordinary success path (`:363–396`), but can return early on error. Its JoinSet wrapper delegates to Tokio; Tokio 1.54.1 `src/task/join_set.rs:591–594` aborts handles on Drop without joining. DataFusion SpawnedTask likewise aborts only (`datafusion-common-runtime/src/common.rs:108–111`). object_store `src/buffered.rs:437–471` commits through PUT or multipart finish. Even without Sail's wrapper, LocalFileSystem `src/local.rs:350–367,882–900` uses `maybe_spawn_blocking` (`src/util.rs:79–87`) for write/rename; started blocking work survives dropping its awaiter. This is a source-level possibility, not a claim that every store behaves identically.

## Registry close, retries and errors

All references in this section are `crates/sail-cache/src/remote_checkpoint.rs` unless named otherwise.

1. `resolve_relation:62–75` checks `closed` once before resolving the path. It grants no tracked operation lease. A caller that already resolved a prefix can retain it after close. Runner admission blocks a later ordinary local execution, but it cannot revoke effects of an earlier admitted execution.
2. `insert:77–97` checks the AtomicBool **before** acquiring the relations write lock. Cleanup sets the flag (`:118`) and later clears the map (`:133,157–162`). A suspended inserter can pass the flag check, let cleanup close/clear, then acquire the lock and publish after cleanup returns. A second check under the same synchronization as close/clear, or a single locked registry state, is required to linearize publication. Acquire/Release ordering does not close this scheduling window. This is an independent registry API race: the ordinary synchronous insert inside an admitted local stream poll is covered by the new runner's wait for that poll, so this audit does not claim that particular local stop path reproduces the race. Direct/concurrent registry users and unqualified cluster shutdown still cannot rely on the registry itself to linearize close.
3. `get:100–105` does not check closed; a descriptor can remain readable while deletion is pending. The current cleanup clears descriptors even when storage deletion fails (`:119–139`). Already cloned descriptor Arcs survive clearing. These are visibility facts that the session state decision must account for, not a prescription to reopen access.
4. Direct `cleanup_session` retry is possible: it does not short-circuit on closed, and retained root/session fields let it resolve and list the same prefix again. `sail-object-store/src/path.rs:32–46` ignores NotFound, but returns on the first other list/delete error; deletion may be partial. A second call can delete remaining visible objects, provided no writer can repopulate the prefix. The registry index has already been cleared after the first storage error. Current actor deletion retains no retry outcome: `session_manager/actor/handler.rs:373–390` spawns the helper and only logs failure.
5. `cleanup_session:137–139` flattens simultaneous storage+registry failures into Internal(String). `sail-physical-plan/src/remote_checkpoint.rs:692–694` likewise flattens checkpoint+relation-cleanup errors. This loses structured/nonretryable cause identity. The existing `DataFusionError::Collection` and Context/Shared wrappers retain both typed errors; `sail-common-datafusion/src/error.rs:185–197` already traverses collections and prioritizes a nonretryable cause.
6. `session_manager/actor/cleanup.rs:7–16` correctly skips checkpoint deletion on any runner.stop error and propagates its typed result. Local stop deliberately reports cleanup errors, not arbitrary query failures (`local.rs:114–122,182–205`). Therefore a checkpoint operation's uncertainty must enter the cleanup/resource report; leaving it solely as the query error cannot block deletion. Sticky local cleanup failure also means a later generic stop call does not itself recover uncertainty.

## Small reviewable prerequisites

Two independent units fit the existing machinery; neither requires a new generic framework.

- **Registry/error correctness:** make close and descriptor insertion mutually ordered; preserve typed combined errors; add exact partial-delete/retry and close-vs-insert tests. This is small and independently useful, but does not join storage effects.
- **Checkpoint effect qualification before delete:** register ownership before the first mutable storage action using the TaskContext's existing TaskResourceScope (`task_resources.rs:128–155`). Keep admitted PUT, multipart creation/parts/completion/abort and compensating relation cleanup reachable until the result is known, even if the stream/result receiver is dropped. Normal completion can report success only after the underlying work is complete. Cancellation must either await confirmed cleanup or report typed cleanup uncertainty through the supervisor, causing existing stop-and-clean to skip prefix deletion. Do not treat a canceled awaiter, a queued abort, the 15-second timeout, or ParquetSink future destruction as confirmed cleanup.

The smallest fail-closed first slice can qualify a started checkpoint effect and report uncertainty when its ownership cannot yet be drained, preserving the session's checkpoint prefix rather than deleting it. That slice must be labeled as a conservative refusal, not completed storage cleanup. A fully successful canceled-delete path requires owned operation completion/abort, including the runtime wrapper and provider boundary. Simply spawning the entire current sink future in a scope is not enough to claim this on error: its internal early exits can still drop child handles, and the storage wrapper can already have detached a mutation.

TaskResourceScope is appropriate for admission, retained shared completion and typed failure (`task_resources.rs:128–175,187–218`); its own documentation `:1–6` explicitly supplies no upload guarantee. An operation may start only when the existing downstream poll initiates it; the scope need not become an eager forwarder of every input row. These are required properties for the next design decision, not a selected upload protocol. Cluster shutdown and arbitrary object-store provider durability remain outside a local-runner result.

## Deterministic fault traces to pin

Use channels/manual polls and an observable completion gate, not sleeps. Existing `runtime.rs:367–454` RecordingMultipartUpload and `:520–535` canceled-completion fixture provide a starting point; existing checkpoint success fixture is `remote_checkpoint.rs:1036–1110`. No existing checked fixture combines a delayed storage effect with local stop and session-prefix deletion.

1. **Late single PUT:** a fake inner store signals entry to put_opts, then waits on a gate before inserting into InMemory. Wrap it in RuntimeAwareObjectStore and start a real checkpoint write through LocalJobRunner. After the entry latch, cancel/drop the stream and await stop. Current unregistered work can permit stop success; prefix cleanup lists no final object and returns. Release the PUT gate and join an observation handle: an object appears after cleanup. The desired qualified path must instead hold stop pending or return cleanup uncertainty that prevents deletion.
2. **Late multipart completion:** reuse the existing completion-start/resume latches, add actual object publication after resume, and hold completion across stop and prefix cleanup. Verify receiver cancellation never becomes a success acknowledgment. Also inject abort failure; do not accept a warning log as a completed cleanup result.
3. **Insert after close:** add a test-only latch immediately after insert's pre-lock closed check. Pause there, run cleanup through map clear, then release insert. Current ordering permits a descriptor after close; corrected synchronization must reject it. A lock-contention sleep is not a deterministic substitute for this latch.
4. **Partial deletion and retry:** a fault store lists two known objects, permits the first deletion and rejects the second once. Assert cleanup Err and closed admission, retain the exact error, then explicitly retry and assert both visible objects absent. Separately hold an admitted writer gate to show retry is insufficient without effect qualification.
5. **Typed compound failure:** inject an original StructuredSparkError or CommitStateUnknownError plus relation deletion failure. Assert exact collection members and CommonErrorCause classification, rather than Collection Display (which prints only its first member). A poisoned private registry lock plus storage failure can separately exercise cleanup_session's dual-error branch.

Scope searched: the remote checkpoint command, planner, registry, physical writers/committer, local runner, current cleanup helper, dynamic/runtime object-store wrappers, matching dependency sinks, and their listed fixtures. This does not assert an exhaustive audit of all table sinks or every external provider.
