# Session deletion: Spark operations and pipeline ownership

Audited Sail `ec8e74d57de51149a774cd4f9048d82039704d0c` through pinned Git objects in `/Users/alexy/src/sail-pipelines-proposal`. Read-only source audit; no build or runtime experiment. All Sail paths below are relative to that checkout and line ranges refer to that commit. This extends `/tmp/sail-sdp-session-deletion-state-audit.md` and the independent checkpoint-effect audit; it does not select a new implementation protocol.

## Finding

`JobRunner.stop()` is a physical-job admission/registered-resource barrier. It is not a complete session-operation barrier. Deletion must also close operation admission, retain in-flight preparation/execution ownership, and wait for effects that escaped stream ownership. Replacing the manager's `Running` entry with `Deleted` does not revoke previously returned contexts, cancel every Spark owner, or prove filesystem quiescence.

Do not overstate the planning gap: pipeline table/view materialization commands *are* routed through the runner; their catalog effects do not execute during physical planning. The concrete storage gap is already-started work detached by cancellation, alongside session-state mutations and operation admission outside the runner.

## Persistent effect boundary, precisely

- Pipeline execution materializes tables/views then runs flows: `crates/sail-spark-connect/src/pipelines/execution.rs:22–39,88–112`. Its `run_command` plans and then calls `JobService.runner().execute`. `crates/sail-session/src/planner.rs:530–532` only creates `CatalogCommandExec`; the command executes in the stream at `crates/sail-physical-plan/src/catalog_command.rs:93–118`. Therefore a sealed runner rejects new materialization commands from an older pipeline run.
- An already admitted TRUNCATE starts ordinary `tokio::task::spawn_blocking` at `crates/sail-catalog/src/command.rs:880–924`, with directory replacement/clearing at909–913. Its handle is only awaited by the command future; it is not registered with TaskResourceScope. Dropping/cancelling that stream can detach still-running filesystem work. Even joining the outer executor after it drops the future does not join that work. This is an actual table-effect counterexample to a broad “no effects after stop” guarantee.
- The independent `/tmp/sail-sdp-checkpoint-effect-audit.md` identifies the analogous checkpoint object-store PUT/multipart/child-task paths. In particular `crates/sail-object-store/src/layers/runtime.rs:75–105,255–266` spawns ordinary handles, and its existing test at520–535 intentionally allows committed upload completion after the caller's completion future is cancelled. Those paths require effect ownership/qualification independently of an operation registry.
- At this pin the pipeline `storage` option is validated (`pipelines/mod.rs:149–153`), but batch pipeline execution rejects incremental table/sink modes (`pipelines/execution.rs:28–35`). No separate pipeline checkpoint lifetime was found in the inspected module. Do not invent streaming/CDC guarantees from these batch paths.

## Required deletion ordering/contract

1. Atomically seal **session operation admission** and publish Closing under the same authority that grants preparation ownership. Include stale-context callers: merely rejecting future manager lookups is insufficient. Cover direct commands, planning, graph-run startup, streaming startup and reattach; no gap between preparation ownership and registration/start.
2. Retain admitted operation owners and all terminal completions in the deletion owner. Signal them and the runner before waiting, so an outer wait cannot be stuck on a paused output or a job that deletion has not yet cancelled. Do not hold the actor/state mutex across awaits. Dropped RPC/interrupt/delete waiters must not relinquish completion ownership.
3. Close physical-job admission and drain its registered resources. Outer operations must not start new effects after their admission has been sealed. Joining an outer owner is sufficient only when its inner work is also joined: unregistered catalog blocking work and detached object-store tasks need their own retained supervision, or must be allowed to settle under a retained owner. “Abort all, then join aborted tasks” does not establish this.
4. Only after both operation/preparation and physical/effect barriers are qualified may deletion clean session checkpoints and report Deleted/success. Any interrupted/unknown cleanup must preserve the typed failure and retryable cleanup owner, and prevent destructive cleanup/false success. Ordinary query failure is distinct from effect-cleanup uncertainty.

This is an ordering requirement, not a demand to wait for every arbitrary Arc to be dropped. Seal capability use and await owned admitted work; external clones may remain but must not admit work. Existing dependency direction matters: `sail-spark-connect/Cargo.toml:21` depends on sail-session, while sail-session has no Spark dependency (`Cargo.toml:10–34`). A protocol-neutral session lifecycle/admission extension or factory hook is consistent with that architecture; directly importing/downcasting SparkSession from sail-session would invert it. The exact shared abstraction and scope need root's design decision.

## Focused regression obligations

- Hold a request after acquiring its context but before graph/executor mutation; close the session, then release the latch. It must either be an owned admitted operation whose effects settle before deletion success, or be rejected before mutation. Test stale-context calls, not only fresh manager lookups.
- Hold executor/run startup between preparation and registration; concurrent close must retain or reject it, never miss it. Include concurrent reattach and an already removed interrupt-owned executor.
- Abandon the first stop/pause/delete waiter during task completion; a second waiter must receive the retained terminal result and no operation may remain permanently Pausing.
- Hold a pipeline between physical jobs and close; no later materialization/write may be admitted. Separately hold admitted TRUNCATE blocking work behind a latch; deletion cannot claim effect completion or clean checkpoints until that handle settles.
- For streaming, distinguish “stream dropped/stopped watch fired” from registered-resource drain success, panic, or uncertain effect completion.
- Verify context/extension retention ends as intended after a paused pipeline is closed; use owned completion and Weak probes rather than elapsed-time assertions.

Existing `python/pysail/tests/spark/pipelines/test_session_graphs.py:46–76` proves graph session isolation and releases in teardown; it does not assert deletion barriers. `79–93` proves independent graph execution/drop. No executor/streaming lifecycle unit tests were found by the bounded search in `executor.rs` and `streaming.rs`; pipeline SQL unit tests concern registration/phase behavior. The recent `sail-session/src/session_manager/actor/cleanup_tests.rs` covers only the narrow runner-before-checkpoint helper, not these outer owners.
