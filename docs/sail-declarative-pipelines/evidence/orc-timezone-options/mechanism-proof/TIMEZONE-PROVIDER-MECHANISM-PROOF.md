# Portable timezone mechanism and native API handoff

This follow-up supersedes the earlier handoff's unconditional statement that
every absent writer zone falls back to the reader zone. Initial fallback and
subsequent inheritance are different, as detailed below.

## Mechanism selected for the next adapter unit

Use dependency-free Java-normalized offset profiles in the optional Sail ORC
adapter. Native ORC receives only immutable timezone/resolver interfaces; it
does not bundle a Java database, consult host timezone data, or add Jiff. Keep
the profile's identity and content pinned in the driver's worker descriptor.
The full profile exporter and Sail adapter are not implemented by this unit.

A profile needs:

- the normalized raw offset before its first explicit Java transition;
- sorted explicit UTC transition instants and total offsets;
- an explicit future policy: fixed offset or a deduplicated Gregorian400-year
  recurring cycle, with an initial offset at cycle position zero;
- the ORC2015 local-midnight epoch in Unix seconds, generated by the pinned Java
  reader's DateFormat semantics;
- exact name/alias mappings and provenance/version/hash.

Native decoding uses the original decoded instant and Java ORC's two-offset
formula, then applies the separately configured precision policy. It never
reconstructs a naive local datetime. Arrow timezone labels remain independent.

## One-profile proof completed

`JavaPortableCycleProof.java` exports only America/Los_Angeles, then compares a
small integer-only portable table reader against public `TimeZone.getOffset`.
The historical table is exported from the pinned ZoneInfo object with offline
reflection. The future cycle is sampled at daily boundaries and transition
instants are bisected to the millisecond; for this profile the resulting800
transitions are independently required to equal every public ZoneRules
recurring transition in years2400..2799. This daily sampling procedure is not
claimed to be a complete exporter for arbitrary zones.

Execution passed306,041 public TimeZone offset comparisons: all explicit
transition boundaries at-1/0/+1ms; daily and midday points over a complete400-year
cycle; cycle boundaries shifted into2000,2400,9600,10000,292000,294000 year blocks
and filtered to the supported future/microsecond range; and22 targeted ORC
conversion boundary cases. The latter compare both UTC-to-LA and LA-to-UTC
adjustments directly against ORC2.3.0 SerializationUtils.

The cycle mapping is:

```
period_ms = 146097 * 86400000
position_ms = (utc_ms - anchor_ms).rem_euclid(period_ms)
```

Apply this only after the final explicit transition for a recurring profile.
Historical instants use the explicit table or stored raw prefix. Thus the Java
Gregorian/Julian calendar cutoff does not leak into negative historical dates:
year1, both sides of October1582, and the minimum microsecond value were checked
against the raw-prefix path. Intermediate arithmetic should use i128 before
narrowing, even though the microsecond input domain fits the millisecond API.

Retained endpoints include:

| Microseconds | UTC instant at floor milliseconds | LA offset |
| --- | --- | --- |
| -9223372036854775808 | -290308-12-21T19:59:05.224Z | -28800000ms |
| 9223372036854775807 | +294247-01-10T04:00:54.775Z | -28800000ms |

The latter's UTC-to-LA result exceeds i64 microseconds; the proof records that
overflow instead of wrapping. Year9999-to10000 conversion remains representable
and matches Java. The independent `portable_cycle_verify.py` reader uses only
integer arithmetic and binary search, and passes all22 retained Java boundary
rows. No Rust engine was built or benchmarked.

Source/results: `JavaPortableCycleProof.java`, `java-portable-cycle-proof.json`,
its `.stdout`/`.stderr`, `portable_cycle_verify.py`, and
`portable-cycle-verification.json`. The Java JSON contains the one profile and

Spark source pin remains617618396087429b5627a86ce933bb0f5d6645cb.

## Names and the ORC epoch

`JavaTimezoneNamesEpoch.java` and `java-timezone-names-epoch.json` retain34 name
cases and their Java2015 epoch. Key cases:

- `PST` resolves to Java's LA rules; `EST` is fixed-05:00; `IST` is India.
- `GMT+5`, `GMT+530`, and `GMT+05:45` are custom fixed offsets. `GMT+23:59` is
  accepted; `GMT+24:00`, `GMT+05:60`, and `GMT+00530` fall back to GMT.
- Bare `+05:30`/`-05:00`, `UTC+05:30`, unknown names, wrong capitalization, and
  leading whitespace fall back to GMT in Java's string API. Do not reuse Sail's
  general SQL timezone parser/alias normalization blindly for ORC writer names.
- Missing/empty ORC metadata is intercepted before that string API and follows
  reader state; it is not equivalent to explicitly resolving the empty string.
- LA's2015 epoch is1420099200, Kathmandu1420049700, LordHowe1420030800, Chatham
  1420020900. Windhoek's epoch1420063200 uses its2015+02:00 offset even though
  its Java normalized raw prefix is+01:00. Store the epoch; do not derive it
  from the profile's prefix offset.

Unknown-name fallback belongs solely to the optional Java-compatible resolver;
the native trait propagates resolver errors and does not invent a fallback.

## Source-checked writer-zone inheritance

New retained Java2.3.0 bytecode: `RecordReaderImpl-javap.txt`,
`TreeReaderFactory_ReaderContext-javap.txt`, `StripePlanner-javap.txt`.

- `TreeReaderFactory_TimestampTreeReader-javap.txt:119-153` initializes ordinary
  TIMESTAMP from JVM default when context writer name is absent. In the baseline
  Spark mode that is the reader timezone.
- The same file`:223-252` shows `getBaseTimestamp(null/empty)` replacing the name
  with the currently held writerTimeZone ID. A later missing stripe therefore
  inherits the most recently started stripe's resolved writer zone.
- `:264-275` uses DateFormat under that writer zone to parse2015-01-01 midnight.
- `:215-219` invokes this update when a non-instant timestamp starts a stripe.
- `RecordReaderImpl-javap.txt:344-395` filters the stripe list by byte offset.
  `:623-653` builds one context/root reader without setting a writer name.
  There is no scan of excluded stripes to seed writer state at a range start.
- `RecordReaderImpl-javap.txt:2110-2200` only starts the batch reader when a stripe
  has selected rows. A predicate-pruned stripe's metadata may be read without
  updating timestamp state.
- `:2977-3032` seeks by reusing that reader and starting the target stripe; it
  does not reconstruct writer state by scanning intermediate stripes.
- `StripePlanner-javap.txt:133-151` supplies the stripe's raw metadata name.

The native API has no random row-seek operation; the implemented state follows
its actual sync/async iteration, byte-range start, and manual row selection.

Public API in `src/timestamp_timezone.rs`:

```
trait TimestampTimeZone: Debug + Send + Sync {
    fn orc_epoch_seconds(&self) -> i64;
    fn offset_millis(&self, utc_millis: i64) -> Result<i32>;
}
trait TimestampTimeZoneResolver: Debug + Send + Sync {
    fn resolve(&self, name: &str) -> Result<Arc<dyn TimestampTimeZone>>;
}
TimestampTimeZoneOptions::new(reader_zone, writer_name_resolver)
ArrowReaderBuilder::with_timestamp_time_zone_options(options)
```

The options are Clone and hold immutable Arcs. Existing Copy
TimestampReadOptions and old constructors retain their behavior. The cursor
starts with reader rules and updates writer state only for started stripes that
contain projected ordinary TIMESTAMP columns. Opt-in stripe construction keeps
raw names and bypasses chrono parsing; default chrono behavior is unchanged.
Instant columns never resolve writer names or apply the conversion. Default
inference gives converted TIMESTAMPs UTC labels; explicit Arrow Timestamp
labels do not alter the reader rules. Decimal128 overrides are rejected in this
mode. Offset queries/candidates use checked i64 milliseconds, adjustment uses
i128 nanos, then existing checked precision conversion narrows the output.

Native predicate row-group pruning is disabled under the opt-in mode, because
`src/row_group_filter.rs:290-303` compares stored UTC timestamp minima/maxima,
which need not bound converted values. Manual RowSelection remains supported.
This suppression does not fix or qualify Sail-side file/stripe statistics
pruning; that must be considered when the adapter is activated.
