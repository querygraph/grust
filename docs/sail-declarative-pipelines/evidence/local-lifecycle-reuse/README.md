# Lifecycle reuse inventory for the Fable discussion

Read-only pins: Grust `d853d4354da53e5887bfe52e6b271ad546da2898`; LakeCat `27e18f390c450c187a34b1c3bb2037c26d107699`. Applicable root `AGENTS.md` files and Grust's `LOCAL-RUNNER-OWNERSHIP-CHECKPOINT.md` were read. Source identities, full Git blob IDs/SHA-256 hashes, and exact excerpt ranges are in `sources.json`; bounded searches are in `searches.json`. No code, dependency graph, protocol, or runtime behavior was changed or selected. Test references below describe existing source assertions; this audit ran no tests.

The reviewed code supplies useful individual ownership and cancellation patterns, but no existing small primitive meets all four checkpoint requirements: admission sealed against stop, independent ownership of a prepared unpolled stream, cancellation-safe shared cleanup completion, and retirement of completed jobs.

| Existing code | Concrete reusable property | Boundary for Sail's checkpoint |
| --- | --- | --- |
| `grust-procedures/src/resources/cancellation.rs:1–87`, `resources.rs:287–341`, `resources/child.rs:133–148,175–196` | Cancellation registration and observation share synchronized state; callbacks run after unlock. Dropped waiters unregister. Children cannot miss parent cancellation; dead weak child entries are pruned on final child Drop. | This is cancellation notification, not completion. Creating a child after cancellation succeeds with an already-cancelled context; it does not reject job admission. It owns neither streams nor async cleanup. Weak-reference pruning tracks final handle destruction, not job completion. |
| `grust-datafusion/src/control.rs:6–39`, `controlled_stream.rs:16–118` | Public cooperative operation/stream wrappers preserve demand-driven polling and pass batches without copies. Terminal poll paths release the upstream stream. | The consumer owns the wrapped stream. An external cancellation merely signals/wakes; upstream is disposed when the consumer polls again or drops it. No owner can independently take a retained unpolled stream. No shared stop completion or job registry. |
| `grust-lancedb/src/write_queue.rs:117–160` | Private `Lead<T>` ownership travels inside the oneshot message before the receiver is polled. Drop hands leadership onward; wake/drop callbacks happen outside the mutex; cancelled receivers are skipped iteratively. | It owns queue leadership and rows, not a prepared query stream. There is no sealed stop/admission state or shared cleanup barrier. Followers receive stringified errors; abandoned commits report uncertain durability as text, so this is not Sail's typed uncertainty contract. |
| `querygraph-memory/src/cognition/sail/worker.rs:27–94` | Private owned worker continues operation/cleanup after its caller is cancelled, and combines primary and cleanup failures. | A single detached task/JoinHandle is not repeatable shared completion. It is tied to staging/dropping a Sail IPC view and hard-coded deadlines; the abort wait can time out and cleanup can itself be dropped at its deadline. It does not own a downstream query stream or guarantee unresolved cleanup remains owned. |
| `grust-turso/src/lib.rs:57–120` | Private group-commit task owns queued jobs independently of submitter waiting; completed batches leave the loop's local ownership. | Unbounded statement queue, no retained task handle, no explicit stop seal or shared terminal wait, and eager database work. It is not a demand-driven stream owner. |

Existing focused test sources provide useful examples: procedure cancellation tests `20–51,88–103` cover live/dropped/reentrant waiters; children tests `583–615` cover late/racing children; controlled-stream tests `40–54,97–105` require another poll or Drop; LanceDB cancellation tests `15–68,106–119` cover unread handoff, uncertain durability, and long cancelled queues; cognition-worker tests `125–156` cover caller cancellation. None asserts the complete local-runner checkpoint contract.

Dependency footprint is determined from the pinned manifests, not a new Cargo resolution:

- `grust-procedures` currently imports `grust-core`, `thiserror`, and `serde_json`; `grust-core` also carries graph models and serialization dependencies including XML/YAML. The cancellation/child algorithms themselves use `std` plus the existing context/error/accounting types. There is no already-extracted standalone lifecycle crate at this pin.
- `grust-datafusion` imports DataFusion 55 with SQL/recursive-protection features, `grust-core`, `grust-procedures`, `grust-arrow`, `futures`, and Tokio; its optional Cypher feature is not required. Its control helpers still depend on procedure-context/error types. Whole-crate import is more than importing the small wrapper source.
- LanceDB's queue source needs `std`, `futures::channel::oneshot`, and Grust error types; the enclosing crate also imports LanceDB 0.30, Arrow 58, and graph adapters. The queue is private. The cognition worker source needs Tokio/`std` plus its session/error interfaces; its unpublished enclosing crate depends on TypeSec, graph code, default Turso, and optional Sail/Arrow integration. Turso's group committer is likewise private and backend-specific. These are source factoring candidates only, not existing minimal public APIs.

LakeCat's reviewed production code contains no matching lifecycle owner. `lakecat-service/src/outbox.rs:46–108` projects persistent events and acknowledges delivery; `lakecat-store/src/memory.rs:1488–1536` marks delivery while retaining event records. Neither is finished-job pruning or a stream/cleanup barrier. Importing `lakecat-service` adds its catalog subsystems, Axum, object-store, and Sail Iceberg dependencies without supplying the missing lifecycle contract. The separate LakeCat manifest records additional exact paths and bounded negative-token searches.

This is a bounded inventory of likely production candidates under `crates`, not proof that no equivalent logic exists anywhere in either repository. Documentation snapshots of Sail's own lifecycle machinery were not counted as independently reusable Grust implementations. The existing Sail `TaskResourceScope` limitations recorded in the checkpoint remain unchanged by this inventory; selecting any new ownership protocol is outside this audit.
