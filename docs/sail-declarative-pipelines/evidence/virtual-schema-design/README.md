# Lazy virtual-schema design checkpoint — not implemented

The user was notified before this batch design phase to allow a switch to Astra. Production Sail remains unchanged and clean at c64533302. This packet is reference research and measured design input, not an implementation/conformance pass.

Spark617618396 separates three operations. CoreDataflowNodeProcessor creates VirtualTableInput from producer identities/resolved flows without forcing a schema. VirtualTableInput.load uses a specified schema directly; otherwise it infers when a consumer requests the table. Only after validateSuccessfulFlowAnalysis does graph validation check declaration compatibility and force remaining schemas. SchemaInferenceUtils merges incoming schemas, then the declaration; that helper is not interchangeable with DataflowGraph.inferredSchema's final direct merge. The source snapshots preserve those distinct call sites.

Twelve dry-run vectors combine declared/untyped, read/unread and no missing source/missing first/missing last, with two incompatible streaming producers. Both owned processes completed and stopped without listeners. Spark produces an unresolved-flow summary in nine cases: an untyped consumer's schema-load failure is direct, while a declared consumer succeeds in analysis and only the independent missing source is reported. Unread tables do not mask missing sources. The other three no-missing cases raise CANNOT_MERGE_INCOMPATIBLE_DATA_TYPE at final schema forcing. Sail instead raises eager UNABLE_TO_INFER_PIPELINE_TABLE_SCHEMA in all twelve. All twelve compared records diverge. Raw fields/messages/events are retained; comparison normalizes namespace only for flow-name lists, not diagnostic fields.

Proposed implementation boundary for Astra review: split virtual input acquisition from final schema validation. Keep temporary/view working plans available where Sail's analysis helpers need them; represent materialized virtual inputs by provider-free incoming schemas, declared schema and producer identities. On GraphScope lookup, return an empty logical relation with the schema actually acquired at that point. A declaration is a valid direct load schema before final compatibility checking; it must never serve as fallback after a failed inferred load. An inferred load failure belongs to the consumer's query outcome/read provenance, not a failure of already-resolved producer flows. After complete query resolution, run Spark's validation phases and final unused-input schema forcing in their source order. Reuse Sail's resolver/scope, schema merge and structured errors, and retain finite plan ownership.

Review before coding: choose a typed working-input representation versus a scope callback compatible with command reanalysis; audit persisted-view versus temporary-view working-plan semantics (do not change their existing ownership accidentally); preserve error identity at each inference/forcing call site; qualify explicit named producers versus implicit same-name flow declaration validation, read/unread outputs, cascaded consumer failures, schema metadata/nullability and no-flow behavior. The raw merge argument ordering differs among measured vectors; whether producer scheduling determines that order needs further qualification. Do not invent a stable ordering by normalizing raw evidence. Do not eagerly compute a schema and merely postpone throwing its error, supply fallback schemas, or report only the first failure. These shortcuts do not implement the measured read boundary.

Suggested reviewable units after design: (1) separate schema acquisition/compatibility APIs with native contracts, (2) scope-backed lazy virtual inputs and failure provenance, (3) explicit post-resolution validation/forcing order and paired regression activation. Keep public streaming/CDC effects disabled. Fable's two original unread-table strict failures remain required; no markers or inventory statuses change here. The design is a proposal with open boundary questions, not accepted activation authority.
