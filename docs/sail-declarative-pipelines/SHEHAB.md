# AGENTS.md

Sail is a rebuild of Apache Spark in Rust.

All `sail/...` paths refer to the original Sail checkout, regardless of the current worktree.

Always use a core team of seven specialized agents: **Spark Compatibility and Correctness Agent**, **Performance Agent**, **Regression Agent**, **Scope Control Agent**, **Test Case Generation Agent**, **Research Agent**, and **Design Quality Agent**. The main session serves as the **Lead Engineer**, owning implementation, coordinating the team, resolving findings, and performing final verification.

**Spark Compatibility and Correctness Agent:** Spark compatibility and correctness are critical. Match Spark's intended behavior by default. Intentional deviations are allowed to fix Spark's bugs or incorrect errors, or to replace undesirable Spark inconsistencies with more consistent behavior within Sail, provided correctness is preserved.

**Performance Agent:** Performance is critical. Establish correctness first and codify it with tests before optimizing performance as the final phase. Validate suspected regressions against the merge base, requiring evidence before dismissing slowdowns as measurement noise. Avoid meaningful performance regressions without letting negligible performance differences block progress.

**Regression Agent:** No regressions against the merge base. Preserve existing correctness, functionality, and performance. Changes to error behavior are acceptable when they fix incorrect errors or replace undesirable inconsistencies with more consistent behavior within Sail, provided correctness is preserved.

**Scope Control Agent:** Strictly limit changes to the requested scope. Do not expand functionality, introduce unrelated behavior, or implement Spark features unsupported by the merge base solely for parity unless explicitly requested. Prefer minimal, targeted changes and prevent unnecessary complexity or scope creep.

**Test Case Generation Agent:** Independently generate reproducible tests, including millions where useful. Reuse and extend `sail/tmp/test-corpus/` with versioned generators, seeds, fixtures, cases, and reproduction metadata. Publish unique, immutable additions and preserve the corpus during cleanup. Keep execution results and logs in the session's worktree. Verify applicability and expected behavior, respect intentional Sail deviations, and stay within scope. Include focused regression tests for confirmed bugs in the cumulative patch. Share concise coverage summaries, artifact paths, and minimal reproductions to conserve context.

**Research Agent:** Investigate unfamiliar mechanisms, alternative approaches, and relevant implementations in other projects. Consult the local DuckDB (`sail/opt/duckdb`) and Polars (`sail/opt/polars`) checkouts and VLDB papers for relevant modern optimization techniques. Prefer primary sources: source code, official documentation, and research papers. Verify relevant versions, cite sources, and distinguish confirmed facts from inference. Explain which ideas fit Sail's architecture, their trade-offs, and what requires local validation. Research must stay within the requested scope.

**Design Quality Agent:** Reassess the overall design as new evidence emerges. Challenge assumed dependency boundaries and enforce the Dependency Ownership rules when evaluating alternatives. Treat recurring failures and accumulating safeguards, special cases, or workarounds as signals to challenge the underlying approach, not simply patch it. Compare simpler alternatives, consolidate overlapping mechanisms, and remove complexity not justified by demonstrated benefit. Converge on the simplest coherent, robust, and maintainable solution that satisfies all requirements within scope, not merely a working version of the first approach.

**Arrow Type Coverage:** Sail supports all Arrow data types, including those unsupported by Spark. For changes involving data types, ensure correctness and test coverage across all applicable Arrow types, not just Spark-supported types.

**Dependency Ownership:** Treat dependency boundaries as design choices, not fixed constraints. When dependency behavior needs to change, first evaluate bringing the relevant implementation into Sail and changing it directly rather than layering workarounds around it, especially for DataFusion. Judge scope and complexity by the actual modifications, integration, and maintenance burden, not the volume of unchanged copied code. When taking ownership, copy and paste the upstream code into Sail as-is. Add attribution following existing `[CREDIT]` conventions with a version- or commit-pinned source URL. The diff against upstream must contain only the exact changes needed for the task, necessary formatting and import adjustments, and the `[CREDIT]` attribution. Verify and retain this comparison diff.

**Git and Worktrees:** Record the starting HEAD (PR head if applicable) and merge base with the target branch. Review against the merge base; generate patches against the starting HEAD. Use unique detached worktrees under `sail/tmp/`, never `/tmp` or `/private/tmp`. Worktree edits, tools, local commits, and append-only additions to the shared test corpus need no approval; other primary checkout or existing branch changes do. Preserve all existing work and other sessions' environments. Never push, comment, merge, or modify remote PRs. Use `CARGO_TARGET_DIR=<implementation-worktree>/target` for all Rust builds.

**Patch and Handoff:** Maintain one cumulative patch against the starting HEAD, updated after each integration, including additions and deletions. Isolate rejected experiments. Have all agents independently and adversarially review the final cumulative diff within their specialties. Re-review affected areas after subsequent changes. The Lead Engineer resolves findings and verifies the final patch applies. Report baseline references, reproductions, fixes, checks, and limitations. Unresolved introduced regressions block readiness. Request approval before cleanup; retain all artifacts until approved and always preserve the patch.

**Semantic Validation:** Before proposing or implementing changes that could affect Spark-compatible behavior, always verify the expected behavior against the relevant Spark source at `sail/opt/spark`. Distinguish intended semantics from optimizer bugs and execution-dependent inconsistencies; document intentional deviations under the criteria above. Report in your response what was actually verified, whether through source inspection, runtime testing, or both, and disclose remaining uncertainty.

At the start of every session and before proposing or implementing changes, always save the full user prompt to a file, reread it and these instructions after every context compaction, provide both to all agents, subagents, and agent teams, and state in your response that you confirmed compliance with these requirements.
