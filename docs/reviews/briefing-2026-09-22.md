# Briefing for an external review: Grust, Nutmeg, and the benchmarks

Written 2026-09-22 for a reviewer who has seen only the Sail extension proposal
(`docs/proposals/sail-extension-api.md`) and its review. It describes what has been
built, what is claimed and on what evidence, what is known to be wrong or open, and
what a review would help most with. Where a number is quoted it comes from a
committed file named beside it; where something is inferred it says so.

## 1. Grust

**What it is.** A Rust property-graph library with one graph, query, mutation, schema
and traversal model over several backends: Memory (the reference), Sail/Spark
Connect, PostgreSQL (plain SQL, pgGraph, SQL/PGQ), Turso, SurrealDB, FalkorDB,
LanceDB, CocoIndex; HelixDB and LadybugDB as unpublished internal adapters.
`grust-cypher` is the portable GQL/Cypher layer: lexer, parser, typed AST,
semantics, reference reads, read pushdown, catalog and transaction surfaces, a
compatibility write planner. Its widest internal profile, `Full39075`, means 72 of
a 77-entry catalog are implemented and tested and five are deliberate strict-write
rejections; it does not mean ISO/IEC 39075 certification or identical execution on
every backend. Memory defines reference behaviour; backend descriptors and live
integration gates say what is pushdown, native, portable fallback or unsupported.

Repository `querygraph/grust`; 22 workspace crates; facade crate `grust-graph`
(library name `grust`). Releases are named and published to crates.io with a book
and a blog post: 0.21.0 "Tadpole" (2026-09-18), 0.22.0 "Mysid" (2026-09-21,
`2182cdb`). `main` is `87fc462`, unreleased 0.23 work.

**The algorithms layer**, which is what the last week built and what the benchmarks
measure (`crates/grust-algorithms`, `grust-procedures`, `grust-algorithm-procedures`):

- `GraphProjection`: a CSR projection (`Adjacency`) of any backend's graph, with
  optional weights, an incoming transpose built on first use or ahead of time
  (`prepare_incoming`), and `NodeProperties` as a sibling structure kernels can
  read. Projection build is parallel by row ranges and byte-identical to the
  sequential build (`db00ee7`).
- Kernels: Mysid announced 33 algorithms; `main` registers 36 procedures
  (`grust.algorithms.<name>` in Cypher, a Rust function over a projection, and
  typed Arrow batches for embedders). Families: PageRank/ArticleRank/personalized
  and weighted variants, WCC/SCC, BFS/DFS/multi-source BFS, Dijkstra, A\*,
  Bellman-Ford, APSP, betweenness (exact and sampled), closeness, degree, k-core,
  k-1 colouring, label propagation, Louvain, Leiden, triangle counting, FastRP,
  link prediction, longest path, topological sort, biconnected components, flow,
  community quality.
- Execution admission: every kernel runs under an `ExecutionContext` with
  `ExecutionLimits` (deadline, work units, memory), a `WorkMeter` that charges
  work as it happens, `Buffer<T>` allocations that reserve memory before use,
  child contexts (`ExecutionContext::child`) for two-level admission (a server's
  budget above a query's), and `Accounting::{COUNTED, WORK_UNCOUNTED, UNCHECKED}`
  so a caller can switch work charging or cancellation off and measure what the
  guarantee costs. Results come out as Arrow with schemas from declarations
  (nullability and signed integers stated, not inferred from data).
- Determinism rules (in `AGENTS.md`): bit-identical results at any worker count;
  float reductions over fixed input partitions, never worker-count partitions;
  a test must reach the parallel path it claims to test; a test that races the
  clock must hold its window on the fastest machine, argued by arithmetic.

**Recent engineering, with the evidence file for each:**

- The PageRank 2.1x gap to a specialised Rust library was attributed (70% a per-arc
  out-degree read, hoisted; 25–29% a transpose timed inside the kernel, moved to
  `prepare_incoming`; ~8% metering) and closed to near parity at protocol sizes
  (`4d8e5db`; benchmark campaigns B3–B5).
- A regression in the path family (+48–117% on some cells) was bisected to the
  parallel projection build, profiled to false sharing on the work-meter balance
  (a bare `Arc<AtomicUsize>` in a 32-byte allocator chunk beside pool
  bookkeeping), and fixed by padding the balance to a cache line
  (`crates/grust-procedures/src/resources/balance.rs`, `87fc462`). B6 measures
  the fix: the cell it targeted went from +117.4% to +0.4%.
- Work charging in the 16 kernels' inner loops was outlined by the compiler in a
  thin-LTO build and cost up to a third; fixed with `#[inline(always)]` and a
  cold deadline sampler (`ca68900`, CHANGELOG "Unreleased").

## 2. Nutmeg

**What it is.** `querygraph/nutmeg`, `main` `c88a0ca`. A Spark Connect server that
embeds Grust's kernels inside LakeSail's Sail (a Rust Spark Connect
implementation), so a PySpark client can stage a graph from a DataFrame
(`df.write.format("nutmeg")`), run a kernel (`spark.read.format("nutmeg")
.option("algorithm", "pagerank")`, or `nutmeg_pagerank('g')` in SQL) and read a
DataFrame back, with no separate graph database and no data leaving the Sail
process. It is built as a replacement for the pattern where a Spark job ships data
to a graph database and back for analytics.

**What `main` does:** node properties reach kernels; opt-in GDS-style column names;
staging accepts joined DataFrames; declared nullability and signed integers;
canonical edge order by default (`order=asStaged` to opt out; 26 of 41 kernel
entries were order-sensitive before, Leiden among them); one memory budget
(`NUTMEG_MEMORY_BYTES`) shared by staging, sorting and projections; per-query child
executions with `timeoutMs`, `workLimit`, `memoryLimitBytes`, `concurrency`; a
streaming `AlgorithmExec` node that runs the kernel at execute time on a bounded
channel and is cancelled by dropping the stream (Sail's interrupt stops a kernel in
~0.03 s); listing functions `nutmeg_graphs()`, `nutmeg_memory()`, `nutmeg_reads()`.
38 integration tests in the default gate.

**Hard limits, stated in its CHANGELOG:** it does not work in Sail's `local-cluster`
or `kubernetes-cluster` modes, because staged graphs are process-local and Sail's
remote-execution codec and stage placement are closed to foreign nodes
(`GRUST-SAIL.md` §7). Dependencies on Grust and Sail are path dependencies
(`GRUST_COMMIT`, `SAIL_COMMIT` record what was verified). Nutmeg is a
`publish = false` project today.

**Showcase:** `examples/citibike/` replicates the shape of Neo4j's Graph Analytics
Spark tutorial on the NYC bike-trip data: stage trips as a station graph in Sail,
run PageRank, weighted PageRank, Leiden (8 communities, modularity 0.440828087),
betweenness and A\*; byte-identical across reruns (`results/rerun-diff.txt`).

**Relationship with Sail**, in `GRUST-SAIL.md`: every Sail change is referenced and
explained: #2374 (Delta MERGE, merged), #2630 (session factory hook, merged,
`e976c8b31`), #2136 (Cypher extension, closed by us), why table functions needed no
change, why performance work was out of scope, a CSV timestamp bug we verified and
commented on (#2522, `SAIL-2522-CSV-TIMESTAMPS.md`; no PR of ours), and why cluster
mode needs no Sail change that a codec hook could provide. The extension proposal
for discussion #2001 is at its fourth revision (`9dd2ae0`), which incorporates the
first external review; it is not posted.

## 3. The benchmarks

All under the neutrality rules in `AGENTS.md` "Benchmark Neutrality": no contest
framing anywhere, every outcome kept distinct, corrections disclosed as
corrections, timings published from a dedicated host only.

**`simple-rust-algo-bench`** (`querygraph/adversarial-graph-algorithms`,
`docker/simple-rust-algo-bench/`, results in `docs/simple-rust-algo-bench-results.md`,
evidence bundles under `docs/simple-rust-algo-bench-evidence/b5-quegee/` and
`b6-quegee/`). In-memory kernels, PageRank, WCC, BFS and triangle counting, on
synthetic fixtures (`hub`, `uniform`, `layered`, `path` at 16,384 and 65,536 nodes;
`hub`/`uniform` at 2M and 4M) at one thread and sixteen. Five participants built
as five distinct binaries in one image: `neo4j-graph` (the `neo4j-labs/graph` Rust
library, f32 scores, no accounting), `icebug` (the Arrow update of NetworKit, C++),
`icecat` (its Rust rewrite), `grustcat` (those kernels over Grust's model),
`grust` (Grust's own kernels over `GraphProjection`, at v0.22.0 and at the commit
under test, in three accounting modes). Protocol: every cell is checked against an
independent Python reference before it is timed; a cell that disagrees is never
timed; steal is read per run and a run with foreign processes ("sightings") is
discarded and kept as such; a cell above 0.25 MAD/median is unusable; the
allocator is pinned only as a labelled probe. Campaigns: B3 (first with
`neo4j-graph`), B4, B5 (`ca68900`), B6 (`87fc462`, 2026-09-22, eight timed runs,
nine parity invocations, all clean).

What B6 established, in the register the texts use: the padding commit closes the
cell it was written for; 47 of B5's 70 slower cells remain slower, 20 of them the
triangles second call, traced to an earlier allocation change; one-worker WCC and
BFS first-call residues are unexplained; every participant, including the C++ and
Rust references, ran slower above L3 than in B5 (+1.3% to +123.1%, cause not
established, so large/xlarge ratios are read within B6 only). Accounting costs 2–9%
at protocol sizes. Beside `neo4j-graph`, first call: PageRank inside L3 Grust is
faster with accounting on or off (hub-65536 one thread 32.41 vs 37.65 ms
unchecked; sixteen threads 4.87 vs 15.18); above L3 slower (hub-2M one thread
3523 vs 2799; hub-4M sixteen threads 749 vs 416); WCC at one worker slower (4.64 vs
3.82); triangles 2x slower at one thread and 7x at sixteen. The two PageRank
columns differ in precision (f32 vs f64) and therefore in iteration count under the
same stopping rule (28 vs 34 on hub); the per-iteration figure is the comparable
one, and an f32 precision option for Grust's kernel is being built so a
like-for-like row exists (campaign B7, planned).

**Publication drafts, not deployed:** a page `/graph/kernels` on adversari.al
rendered from the B6 bundle by a script that fails the build on any hand-typed
number (`adversarial-site` branch `work/simple-rust-algo-bench-b6`, `88891b7`); a
post regenerated byte-for-byte from the bundle (`work/simple-rust-algo-bench-b6`,
`fe50ea8`); `docs/related-work.md` updated.

**Other benchmarks in the family:** LSQB (`benchmarks/lsqb` in Grust: labelled
subgraph queries across backends, with execution classes disclosed); the strain
benchmark (`querygraph/adversarial-graph`, admission and resource envelopes under
load); both published on adversari.al/graph with the same evidence discipline.

## 4. Known errors and how they were caught

Recorded because a reviewer should weigh the process, not only the artefacts.

- The #2001 proposal went through three adversarial citation reviews (26, 22 and 7
  findings) before the external architecture review; each found claims written
  from memory rather than from a source (a false statement about pysail, altered
  quotes, a wrong optimizer anchor, an unmeetable proof-of-concept condition). The
  external review then found a different class of gap: execution-semantics
  contracts the citation reviews could not see. The fourth revision is organised
  around those contracts.
- A deadline test passed on a laptop and failed the Linux gate, was fixed, and
  failed on 16 cores because the "endless" kernel reached an exact fixed point; the
  rule now in `AGENTS.md` came from that.
- A benchmark column was once labelled backwards from a directory listing; the
  participant-lineage document exists because of it.
- A stale build directory produced a release-blocker story two agents endorsed;
  the rule is now to run the cheapest refuting experiment before reporting a cause.

## 6. What a review would help most with

1. **Grust's admission model.** Is two-level admission (server budget, then query
   child contexts, `MemoryReservation::shrink`, work charged inline with a cold
   deadline sampler) the right shape for an embedded engine, and what does it miss
   that a Spark executor would need?
2. **Determinism as a product property.** Bit-identical results at any worker count
   forced fixed-partition reductions and a canonical edge order in Nutmeg; is the
   cost (some parallel speedup, sorting on stage) justified, and are there kernels
   where the rule is too strong or not strong enough (Leiden's refinement order,
   FastRP's random projections)?
3. **The benchmark protocol.** Parity gate, steal and sighting rules, MAD threshold,
   allocator probe, "read within campaign" when host state drifts: what would an
   adversarial reader still reject, and what is the smallest change that would
   answer them? The above-L3 drift with cause not established is the open wound.
4. **The f32 like-for-like row.** Is matching precision and stopping rule enough to
   call two PageRank columns comparable, or must iteration count be fixed too?
5. **Nutmeg's placement bet.** In-process residency on the driver (§4.3 and §7.5 of
   the proposal) trades a second deployable for a driver bottleneck; is there a
   design that keeps zero-copy without driver residency?
6. **What we are not measuring** that a user of a Spark graph-analytics pipeline
   would ask about first.
